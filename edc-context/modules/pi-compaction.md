# pi-compaction module context

## When To Read This
Read this when changing async-compaction behavior, Pi extension hook wiring, background job state, validation/handoff logic, provider auth forwarding, or the experimental adapter API. Do not use it as a replacement for Pi's own compaction implementation: this package intentionally mirrors and delegates to Pi, so exact compaction semantics must be checked against the pinned `@earendil-works/pi-coding-agent` source/types and parity tests.

## Ownership And Authority Boundaries
- This package owns only an in-memory precompute lifecycle around Pi compaction: start thresholds, pending/ready/stale/failed state, status-line text, timeout/cancel handling, safe apply decisions, adapter registration, and marker/correlation metadata. Source: `src/job.ts`, `src/core.ts`, `src/runtime-state.ts`.
- Pi remains the persistence and apply authority. Ready summaries are handed to Pi through `session_before_compact`; Pi persists the resulting `CompactionEntry` and emits `session_compact` / `session_compact_failed`. This module must not be treated as writing durable session state directly. Source: `src/core.ts:133-195`; Pi event contracts in `node_modules/@earendil-works/pi-coding-agent/dist/core/extensions/types.d.ts`.
- Built-in summaries are generated by Pi's exported `compact()`; this module locally reconstructs `CompactionPreparation` because the public top-level package entrypoint does not expose Pi's full preparation helper. Source: `src/preparation.ts`, `src/job.ts:45-80`, `ASYNC_COMPACTION_DESIGN.md`.
- Adapter authors own the semantic correctness of `prepare`, `createSnapshot`, `run`, and `toCompaction`; core owns lifecycle and generic validation only. Adapter results get a non-empty-summary check and marker insertion, not package-specific semantic validation. Source: `src/adapter.ts:33-40`, `src/job.ts:400-408`, `docs/async-compaction-adapters.md`.

## Core Runtime Model
There is one runtime state object per adapter registration. Normal flow is `idle -> pending -> ready -> idle`, with terminal/side states `stale` and `failed`; pending jobs are not replaced, while ready jobs can be reused or staled/replaced after validation drift. `markStale` aborts any background signal and clears apply/handoff/autoresume correlation, so callers relying on those fields after invalidation are already wrong. Source: `src/runtime-state.ts:38-63`, `src/job.ts:345-423`.

Automatic start happens after `turn_end` only when async is enabled, a model exists, Pi compaction settings are enabled, context usage is known, and usage is inside the early-start window but not past Pi's final reserve boundary. Manual `/async-compact-now` bypasses the early-start window but not the enabled/model/settings/preparation/pending guards. Source: `src/core.ts:113-115,202-210`, `src/job.ts:304-376`.

A ready result is applied only if it still validates and either Pi is idle with no queued messages or an active turn is abortable, has no queued messages, and is above the async threshold. In the active-turn path, core sets `autoResumeAfterCompaction`, calls `ctx.abort()`, then triggers `ctx.compact()`. It sends `continue` only after a marker-correlated `session_compact` confirms Pi persisted this extension's compaction and only if no user/queued message arrived before the deferred send. Source: `src/job.ts:149-174`, `src/core.ts:170-188`; covered by `test/index.test.ts` and `test/job-start.test.ts`.

## Snapshot And Validation Contracts
A ready job is valid only for the same session, active model key, thinking level, compaction settings key, first-kept boundary, and branch ancestry observed at snapshot time. Appended tail after the snapshot is allowed only while the current branch still contains both `firstKeptEntryId` and `snapshotLeafId` in order; the first kept entry must not be a tool-result entry; custom `/compact <instructions>` forces fallback to Pi synchronous compaction. Source: `src/validation.ts:25-80`, `test/validation.test.ts`.

The preview-size check builds a synthetic compaction entry over the current branch and estimates the resulting context before handoff. This is the guard that prevents a once-valid ready summary plus newly appended tail from exceeding Pi's post-compaction reserve budget; do not replace it with checking the original snapshot size. Source: `src/validation.ts:7-23,64-67`, `test/job-replacement.test.ts`.

Correlation is three-part (`adapterId`, `jobId`, `promptVersion`). Notifications, apply failures, and auto-resume are ignored unless the persisted/failed compaction is extension-provided and matches the last handed-off correlation. This prevents claiming other extensions' compactions or stale markers from old jobs. Source: `src/core.ts:52-65,170-195`, `src/job.ts:186-213`, `test/index.test.ts`, `test/core.test.ts`.

## Preparation Parity Constraints
`prepareAsyncCompaction` should remain a structural mirror of Pi's normal preparation behavior: it refuses to prepare when the leaf is already a compaction, derives the previous-summary boundary from the latest compaction, delegates cut selection to Pi's `findCutPoint`, preserves split-turn prefix semantics, and returns no preparation when there is nothing to summarize. Source: `src/preparation.ts:61-129`; Pi reference in `node_modules/@earendil-works/pi-coding-agent/dist/core/compaction/compaction.js`; sentinels in `test/pi-parity.test.ts`.

File-operation continuity is intentionally selective. It inherits `readFiles`/`modifiedFiles` from prior Pi-generated compactions and this package's own async compactions, but not arbitrary foreign extension compactions. New file ops are extracted only from assistant tool calls named `read`, `write`, or `edit` with a string `path`. Source: `src/preparation.ts:15-33,104-117`, `test/preparation.test.ts`.

`tokensBefore` uses usage-aware accounting: last successful assistant usage is authoritative, with estimated trailing tokens added; aborted/error/zero-usage assistant messages are skipped and the function falls back to estimating all messages when no valid usage exists. This exists to match Pi's context accounting, not to be a fresh cost metric. Source: `src/utils.ts:121-144`, `test/preparation.test.ts`, `test/pi-parity.test.ts`.

## Provider/Auth Boundary
`buildAsyncCompactionResult` must use `ctx.modelRegistry.getApiKeyAndHeaders(model)` immediately before `compact()`, then pass Pi's resolved API key, raw nullable headers, resolved environment, retry policy, and resolved base URL/request headers. The apparent mismatch is deliberate: nullable provider headers are normalized for the request model but forwarded raw to Pi's `compact()` compatibility boundary so header deletions/casing semantics survive. Do not simplify this without updating the auth/header tests. Source: `src/job.ts:36-80`, `test/job-start.test.ts`.

External calls that can fail or hang are deliberately contained by state correlation and abort signals: provider/auth resolution and `compact()` failures become background failures while pending; `ctx.compact({ onError })` failures are recorded only for the current in-flight or last-handed-off job; timeout aborts become stale rather than failed. Source: `src/job.ts:201-232,285-301,390-423`, `test/job-failure.test.ts`, `test/job-timeout.test.ts`.

## Adapter API Fragility Points
- Adapter IDs are part of job IDs/status keys and persisted markers; registration rejects IDs outside the safe lowercase/digit/dot/underscore/hyphen shape and rejects duplicate IDs per `ExtensionAPI` object. Source: `src/core.ts:38-73`, `test/core.test.ts`.
- `prepare()` must snapshot stable data, not live mutable session references. Core may run `run()` later with only an abort signal and later validate using the generic `Snapshot` fields. Source: `src/adapter.ts:9-40`, `docs/async-compaction-adapters.md`.
- `toCompaction()` output details are preserved, then `details.asyncPrefixCompaction` is added/overwritten by core. If an adapter needs a field named `asyncPrefixCompaction` for other purposes, it conflicts with core ownership. Source: `src/job.ts:253-283`.
- Lifecycle observers are diagnostic only: they are synchronous, exceptions are caught and logged, and `wastedWork` is qualitative (`possible`/`confirmed`), not billing/token accounting. Source: `src/diagnostics.ts`, `docs/async-compaction-adapters.md`.

## Test And Debug Routing
- Run `bun test` for behavioral coverage; `bun --check src/*.ts` and the package `typecheck` script catch API/type drift.
- Use `test/pi-parity.test.ts` when touching preparation, token accounting, file-op inheritance, or Pi dependency versions. The real long-session parity case is opt-in via environment flag.
- Use `test/index.test.ts`, `test/job-start.test.ts`, `test/job-replacement.test.ts`, `test/job-failure.test.ts`, and `test/job-timeout.test.ts` for state-machine, safe-apply, auto-resume, and error-path changes.
- Use `docs/async-compaction-adapters.md` as the public contract for adapter-facing changes; update it with `src/core.ts`/`src/adapter.ts` changes.
